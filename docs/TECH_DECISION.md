# TECH_DECISION — 技术决策记录

每条记录：**决定 → 备选 → 为什么 → 代价 → 什么时候该推翻它**。

---

## TD-1 构建工具：手写两份 Vite 配置，而不是 WXT / Plasmo / CRXJS

**决定**：`vite.config.ts`（页面 + service worker，ESM）+ `vite.content.config.ts`
（content script，IIFE 单文件）+ 一个 20 行的 manifest 校验脚本。

**备选**：WXT（read-frog 用的就是它）、Plasmo、`@crxjs/vite-plugin`。

**为什么**：这些框架的主要价值是自动生成 manifest、HMR 和多浏览器适配。而本项目的 MVP
只有 3 个页面 + 1 个 worker + 1 个 content script，框架带来的是**不透明的构建产物**和
一个会跟着 Vite 大版本晃动的依赖。手写配置总共 70 行，产物路径完全可预测，出问题时
`dist/` 里看到的就是我写的东西。

**代价**：没有 content script 热更新（改完要在 `chrome://extensions` 点一次刷新）；
将来要适配 Firefox 得自己处理差异。

**什么时候推翻**：需要同时发布 Chrome / Firefox / Edge，或者 content script 迭代频繁到
手动刷新变成主要成本时，换 WXT。

## TD-2 content script 用 React + shadow DOM

**决定**：注入 React 应用到 shadow root，样式以 `?inline` 字符串注入。

**备选**：原生 DOM 操作（体积小很多）、iframe 隔离（隔离最彻底）。

**为什么**：卡片有真实的状态机（pill → loading → result/error → saved），还要处理
乱序响应和键盘/滚动/外部点击。用原生 DOM 手搓这套状态同步，代码量和 bug 率都更高。
iframe 隔离最干净，但定位、尺寸自适应、焦点管理都要额外一层协议，得不偿失。

shadow DOM 解决了这类扩展最常见的两个投诉：宿主页样式污染浮层，以及浮层样式泄漏进宿主页。

**代价**：content script 打包 282KB（gzip 86KB），比原生实现大一个量级。它在
`document_idle` 注入，不阻塞页面渲染，但确实占内存。

**什么时候推翻**：如果要在低端设备或超重页面上做性能优化，可以把 UI 换成轻量方案，
或把 React 延迟到首次划词才加载。

## TD-3 Provider 抽象：接口薄、共享层厚

**决定**：`AIProvider` 只有四个方法；prompt、schema、JSON 修复、HTTP 与错误映射全部共享；
各家实现只负责 transport + auth + 结构化输出的方言差异。

**备选**：直接用 Vercel AI SDK（`ai` + `@ai-sdk/*`）统一多家模型。

**为什么**：AI SDK 很好，但它会把四家 provider 包全拉进扩展包，而我们只需要
"发一个 JSON 请求、拿一个 JSON 回来"。更重要的是：**语境解释的 prompt 就是这个产品**，
它必须只有一份、可被 review、不随 provider 漂移。抽象层放在我们自己这一侧才有这个保证。

**代价**：新增一家 provider 要自己写一个类（约 100 行）。流式输出没有做（见 TD-8）。

**什么时候推翻**：要支持十家以上模型、或需要工具调用/流式/多模态时，换 AI SDK 更划算。

## TD-4 Claude 用官方 SDK，其余用 fetch

**决定**：`@anthropic-ai/sdk` + `client.beta.messages.parse()` + `betaZodOutputFormat`；
OpenAI / DeepSeek / Gemini 用原生 `fetch`。

**为什么**：Anthropic 官方 SDK 提供了结构化输出解析、类型化错误类和重试；OpenAI 兼容协议和
Gemini REST 都足够简单，为它们各引一个 SDK 只是徒增体积。SDK 只进 service worker 的 chunk，
content script 里没有它（构建产物已验证）。

具体配置及其理由：

- 模型默认 `claude-opus-5`；
- `output_config.effort: 'low'` + 保持自适应思考开启。查词是低难度、强延迟敏感的任务，
  用降低 effort 来提速，而不是关闭 thinking——官方文档明确指出关闭思考会导致推理标签泄漏进
  可见输出；
- 开启服务端拒答回退（`fallbacks: 'default'`）。阅读助手会指向用户正在读的**任何**内容，
  查到俚语、脏话、漏洞名称是完全正常的场景，一次拒答对无辜的学习者就是一次硬报错。
  如果账号不支持该 beta，第一次 400 后自动降级并记住，最多多花一次往返；
- `dangerouslyAllowBrowser: true`：调用发生在扩展自己的 service worker，Key 来自
  `chrome.storage`，从不进入网页上下文。

## TD-5 默认离线词典（Mock Provider），且必须诚实

**决定**：`mock` 是默认 provider，内置几十个技术阅读高频词 + 启发式词形还原；同时作为
所有 provider 失败时的兜底。

**为什么**：装上扩展的前 30 秒决定了用户是否留下。要求先去注册 API Key 才能看到任何东西，
会流失掉大部分人。离线模式让"划词 → 解释 → 收藏 → 复习"整条闭环立刻可跑。

**关键约束**：离线模式**不能假装自己理解了上下文**。词库未收录时它直说"离线词典未收录该词"，
并把原句原样回显 + 提示去配置 Key；不编造音标，不编造释义。假装比无能更伤害信任。

**代价**：多维护一份小词库。

## TD-6 复习算法：四档阶梯，而不是 SM-2 / FSRS

**决定**：0/1/2/3 四档熟悉度 + streak 拉长间隔，纯函数、注入时钟、100% 单测覆盖。

**为什么**：SM-2 的 ease factor 需要几十次复习才有统计意义；用户手工收藏的规模是几百词、
每词几次复习，参数学不出东西。四档的另一个好处是**可解释**：UI 上就写"陌生/学习中/熟悉/掌握"，
每个打分按钮直接显示"下次什么时候再见"。前一个月的实际间隔和 SM-2 差异很小。

**代价**：长期（半年以上、上千词）的调度效率不如 FSRS。

**什么时候推翻**：`ara:reviewLog` 攒够数据后，可以直接拿它离线评估 FSRS 是否更优——
复习流水从第一天就在记，正是为了这个。

## TD-7 扩展页面直连 storage，不走 background

**决定**：popup / options / app 直接调用仓储层 + 订阅 `chrome.storage.onChanged`。

**为什么**：它们与 worker 同权限，绕一圈只增加延迟；而 `onChanged` 免费给了跨页面实时同步——
在网页上收藏一个词，已打开的单词本立刻出现新条目。而且 worker 被回收时页面不受影响。

**代价**：写逻辑存在于两条路径（页面直写、worker 代写），必须共用同一套仓储函数和写锁，
不能各写各的。这一点靠"业务规则只写在 `storage/` 与 `services/`，`background/` 只做路由"来保证。

---

## TD-8 不做流式输出

**决定**：解释请求一次性返回。

**为什么**：输出是**结构化 JSON**（十来个字段），流式渲染一个半成品 JSON 对用户没有价值——
不像聊天那样逐字有意义。字段填不满的卡片反而更慌乱。当前 loading 骨架屏的心理等待感更好。

**什么时候推翻**：如果加入"整段讲解""长难句拆解"这类长文本输出，那时流式是必需的。

---

## TD-9 手写 JSON Schema，而不是从 zod 生成

**决定**：`schema.ts` 里 JSON Schema 和 zod schema 各写一份。

**为什么**：OpenAI 的 strict 模式要求 `additionalProperties: false` 且所有字段 required；
Gemini 用的是 OpenAPI 子集（类型名大写、不认 `additionalProperties`）。自动转换器在这些
边角上各有出入，调试成本高于手写。而校验侧的 zod 需要大量 transform（把 `null`、缺字段、
数组里的空串都修好），转出来的 JSON Schema 反而是错的。

**代价**：两份定义要手动保持同步。缓解手段：给需要转 zod→JSON Schema 的 SDK 单独准备了
一份无 transform 的"纯净版" schema；`WORD_EXPLANATION_KEYS` 是唯一的字段名清单。

## TD-10 上下文抽取用"偏移 + 向外扫描"，不用正则切句

**决定**：先求出选区在文本块内的字符偏移，再向两侧扫描到句子边界，并带缩写守卫。

**为什么**：`split(/(?<=[.!?])\s+/)` 会在 `e.g.`、`Dr.`、`v2.5`、`node.js` 上切错，而
**句子正是整个产品的输入**——切错一次，模型就在错误的上下文里解释。守卫规则很简单：
点号后面不是空白就不是句号（覆盖 `e.g`、`v2.5`、`U.S.A`），后面是空白则查缩写表。

**代价**：仍是启发式，不可能全对。所以段落级 `wideContext` 也一并存下来作为兜底。

## TD-11 只用 `chrome.storage.local`，一个 key 装整张词表

见 [DATA_MODEL.md §7](DATA_MODEL.md#7-取舍记录) 的完整论证：`storage.sync` 装不下带原句的
词条，也不该把 API Key 同步到 Google 账号；IndexedDB 在目标规模下是过度设计，而
`StorageAdapter` 抽象让将来切换只影响一个文件。

## TD-12 图标由代码生成

**决定**：`scripts/generate-icons.mjs` 用 zlib 手写一个最小 PNG 编码器，按距离场绘制圆角
渐变底 + 白色 "A"。

**为什么**：Chrome 只接受位图图标。把四个二进制文件签进仓库，等于把品牌标识变成不可修改的
黑盒；改一次颜色就要重新找设计工具。生成脚本让图标变成可 review、可 diff 的代码，
且不引入任何图像依赖。

**代价**：脚本约 150 行；复杂图形（真正的 logo）不适合这么画。

## TD-13 三层验证，其中一层跑在构建产物上

**决定**：类型检查 → 纯逻辑单测 → **对 `dist/assets/background.js` 的冒烟测试**。

**为什么**：Chrome 扩展最难受的失败都发生在打包之后：监听器没注册、node 内置模块被
stub 成 `{}`、消息信封结构对不上、manifest 指向不存在的文件。这些单元测试一个都抓不到。
冒烟测试用一个假的 chrome API 加载真实产物，跑完
`explain → 缓存命中 → save → 合并 → lookup → remove` 全链路。

**代价**：假 chrome API 需要跟着用到的 API 增长而维护。

**已经抓到的问题**：写测试的过程中抓出两个真 bug——`hard` 评分同时降级又累加连击；
句子扫描在 `e.g. SQS` 处截断。两个都写进了回归测试。

## TD-14 从 read-frog 源码分析中直接采纳的四条修正

[READ_FROG_ANALYSIS.md](READ_FROG_ANALYSIS.md) 完成后，有四条结论直接改了代码——记在这里是因为
它们都属于"不看别人踩过的坑就不会想到"的类别。

**① 注入 UI 必须标 `notranslate` / `translate="no"`（分析 §7.13）**
我们的目标用户恰恰是最可能同时装着沉浸式翻译类扩展的人。不标记的话，别人的翻译器会走进我们的浮层，
把 AI 写的中文解释再"翻译"一遍。两行代码，不做就是 bug 报告。

**② prompt 版本必须进缓存 key（分析 §7.15 / §9.2）**
原实现的 key 是 `(providerId, model, text, context)`。read-frog 把 `modelRevision` 哈希进持久缓存 key，
理由同样适用于我们，而且更严重：**我们会频繁迭代 prompt**，忘了这条，改进后的 prompt 对老用户
最长 30 天不生效。现在 `PROMPT_VERSION` 是 key 的一部分，改 prompt 时同步 bump。

**③ 构建期扫描产物中的凭据（分析 §7.17）**
read-frog 有一个 `check-api-key-env` 插件，在生产构建发现任何非白名单的 `*_API_KEY` 环境变量时直接
让构建失败，理由是"扩展 zip 人人可解压"。我们的做法更直接：构建后扫描 `dist/` 全部文本产物，
匹配到 `sk-ant-` / `sk-` / `AIza` / `ghp_` 形态的字符串就让构建失败。我们本来就不内联任何凭据——
**正因如此，一次意外内联不会有任何人察觉**，所以这道闸门是必要的。

**④ popup 首屏不能先渲染 0 再跳变（分析 §7.18）**
popup 只有约 200ms 的第一印象。原实现先渲染 `0 收藏 / 0 待复习` 再被真实数据替换，读起来像扩展坏了。
现在数据未就绪时显示 `—`。

未采纳但记录在案的两条（见 [TODO.md](TODO.md) 阶段 2）：
- **两层缓存**（L1 含上下文的完整解释 + L2 与上下文无关的词条基础信息）。当前只有 L1，命中率偏低，
  但实现简单且语义清晰；等有真实使用数据再拆。
- **词条内嵌 `schemaVersion`**。当前 schema 版本是全局的（`ara:meta`），解释结构一旦变化，
  历史词条需要按版本走不同渲染分支才能保真。

## TD-15 GitHub 同步用 Personal Access Token，不用 OAuth

**决定**：用户在设置页粘贴一个 classic PAT（勾选 `repo`），扩展用它调用 `api.github.com`：
校验身份 → 仓库不存在就创建为私有 → 双向同步。

**备选**：OAuth Device Flow。

**为什么不用 OAuth**：两个硬问题。其一，device flow 需要一个已注册的 OAuth App，它的 `client_id`
必须打进扩展包——这要求我们（而不是用户）去注册并长期维护一个 App，一旦被滥用会牵连所有用户。
其二，GitHub 的 token 端点（`github.com/login/oauth/access_token`）对浏览器上下文的 CORS 支持
并不可靠，扩展直连很可能拿不到 token，那就得再架一个中转服务——而"没有服务器"是这个产品的隐私前提。

PAT 的代价是用户要手动去点一次生成令牌；换来的是整条链路只有"用户浏览器 ↔ api.github.com"。
设置页里的链接已经预填了 `scopes=repo`，把这一步压缩到两次点击。

**代价**：PAT 权限比 OAuth 粗（classic `repo` 能读写用户所有仓库）。fine-grained token 更细，
但它无法创建仓库，用户得先手动建好私有仓库再授予该仓库 Contents 读写——文档里说明了这条路径。

## TD-16 同步产物是三个文件，且必须是确定性的

**决定**：每次同步写 `vocabulary.json`（机器）+ `VOCABULARY.md`（人）+ `README.md`（统计），
内容逐字节比对，没变就不提交。

**为什么**：把知识库放进 Git 而不是对象存储，唯一的理由就是 **diff 和历史**。如果只推一个
JSON blob，`git log` 毫无意义。`VOCABULARY.md` 按字母分组、条目内不含易变字段，所以一次提交的
diff 读起来就是"这周我学了哪些词"。

**踩到的坑（已被单测钉住）**：`buildSnapshot()` 会把 `exportedAt` 写成当前时间。这对手动导出是
对的，对同步是毒药——文件每次都不同，开着 30 分钟自动同步的用户，仓库里会每天多出 48 个只改一行
时间戳的提交，把 commit 历史彻底淹没。现在同步用的时间戳由数据本身推导（所有词条与复习记录里的
最大 `updatedAt`），语义是"数据截至何时"，且天然稳定。

**同理刻意排除**：`VOCABULARY.md` 不打印 `dueAt`——复习一张卡就重写整个文件是同样的噪音。

## TD-17 同步顺序永远是 拉取 → 合并 → 推送

**决定**：`runSync()` 先拉远端快照并 `importSnapshot` 合并进本地，再推送合并后的完整状态。

**为什么**：反过来（先推）会让一台新装的设备（本地为空）在第一次同步时，用空数据覆盖用户积累了
几个月的远端仓库。合并本身是加法语义（同 `normalized` 冲突时保留复习次数更多的一方），所以最坏
情况是多留了一条记录，而不是少了一条。

**一条硬规则**：如果远端 `vocabulary.json` 存在但无法解析，**中止同步并报错**，绝不覆盖。
读不懂的文件里可能装着用户全部的资产。

## TD-18 知识库仓库按首字母分片，并用 Git Data API 单次提交

**决定**：仓库布局改为 `index.json` + `vocabulary/<字母>.{json,md}` + `meta/*.json`；
写入走 Git Data API（blob → tree → commit → ref）。

**触发原因不是整洁，是一个硬上限**。实测一条词条约 2.5 KB（`source.context` 与
`wideContext` 占大头），于是：

| 词条数 | 单文件大小 | |
|---|---|---|
| 500 | 1.2 MB | **已越过 GitHub Contents API 读取单文件的 1 MB 上限** |
| 3000 | 7.3 MB | |

也就是说单文件方案在几百词时就会让**拉取直接失败**，而不是"以后变慢"。

**为什么按首字母**：命中率高、规则简单、用户能看懂目录。英文首字母分布很不均
（s≈11%，x≈0.1%），所以最大分片约是全库的 1/8——3000 词时约 860 KB，仍在安全区；
而读取改走 Blobs API 后本来也没有 1 MB 限制。

**为什么必须同时换 Git Data API**：Contents API 是**一个文件一次提交**。分片后每次同步
会产生几十个 commit，直接毁掉「commit 历史就是学习记录」这个产品主张。Git Data API
把任意数量的文件变更打成一次提交。

**顺带拿到的好处**：git 的 blob sha 可以在本地算，与远端 tree 列表比对即可判断哪些文件
真的变了。稳态下一次同步 = 一次 tree 列表请求 + 零上传 + 零下载。

**迁移**：检测到旧的 `vocabulary.json` / `VOCABULARY.md` 时，先把其中的词条合并进来，
再在**同一个提交**里写出分片并删除这两个旧文件。用户无需做任何事。

**本地存储没有跟着分片**（`chrome.storage.local` 仍是一个 key 装整张词表）。同样按
2.5 KB/词 估算，3000 词约 7 MB，已申请 `unlimitedStorage` 所以不受配额限制；代价是每次
收藏都要整体重写一次。真正该换的信号是写入延迟变得可感知，届时按同样的分片键切到多 key
或 IndexedDB——`StorageAdapter` 抽象就是为这一天准备的。**在没有实测到延迟之前不做，
是因为它会把每个读取路径都变复杂，而收益目前只是理论上的。**

## TD-19 多设备：拉取在前，删除用墓碑，丢掉竞态就重来

**决定**：同步顺序恒为 拉取 → 合并 → 推送；删除写成带时间戳的墓碑；ref 更新被拒时
整轮重做一次。

**三个问题，三条规则**：

**① 顺序**。推送在前会让一台刚装好的设备（本地为空）覆盖掉远端几个月的积累。
拉取在前的最坏情况只是多留了一条记录，而不是少了一条。

**② 删除**。这是多设备下最刺眼的 bug：在 A 电脑删掉的词，B 电脑同步时会把它加回来——
因为 B 从来不知道你删过。所以删除不能是"把行去掉"，必须留下一个带时间戳的墓碑并同步出去。
冲突规则：删除时间晚于对方最后修改时间才生效；反过来，**更晚的一次保存能覆盖更早的墓碑**，
否则用户重新查到并收藏的词会在下一次同步时凭空消失。墓碑在同步成功 30 天后清理——
到那时它必然已经传播到了每台设备。

**③ 竞态**。我们读 tree、合并、然后用旧的 head 作为 parent 提交。如果另一台设备在这中间
推送过，GitHub 会拒绝这次非 fast-forward 的 ref 更新——这完全正确，因为我们的提交建立在
一个已经不是 tip 的父提交上，落地就会丢掉对方刚推的东西。两台设备下丢掉竞态是常态，
所以正确的反应是**基于新的 tip 重做整轮**，而不是把错误抛给用户。

**测试上的一个教训**：假 GitHub 最初在创建 tree 时就把文件落盘了，于是重试用例永远通过——
因为第一次尝试已经把内容写进去了。真实的 GitHub 要等 ref 更新成功才把 tree 发布到分支上。
把这个语义补进 fake 之后，这个用例才真的在测东西。
